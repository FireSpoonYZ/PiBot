# pibot-host

Standalone Rust supervisor and pairing CLI for the bundled `pibot` Host service.
All machine output is a single JSON line on stdout; failures print
`{"error":{"code","message"}}` and exit non-zero.

## Subcommands

- `pibot-host run` — Foreground windowless supervisor that locks `HOST_HOME/launcher.lock`, spawns the bundled Node runtime (`pibot-node` + `host-runtime/host-core/host-service-cli.js serve`), rotates `HOST_HOME/logs/host.log` at 10 MiB, and restarts the Host with exponential backoff on unexpected exits.
- `pibot-host start | stop | restart | status` — Background service lifecycle control. On Windows `start`/`status` go through the `ELauncherHost-<SID>` scheduled task below (never a plain `spawn run`); on Linux they delegate to `systemctl --user` when `e-launcher-host.service` is installed. `stop` asks the Host for a graceful shutdown over its existing Node stdin channel first, with the outer timeout larger than the Host's own cleanup budget. `status` reports `running` (supervisor alive), `ready` — an authenticated `GET /v1/service` probe of the local Host with a short timeout, so a merely listening port never counts as ready — plus `autostart`, `autostartScope:'user-login'` and `platform`.
- `pibot-host enable | disable` — Login autostart (`autostartScope:'user-login'`). Windows: routed through the bundled `shower-windows.exe host-task install|enable|disable|remove`, which manages the fixed `ELauncherHost-<SID>` task for the current interactive user (fixed action `pibot-host.exe run`, trigger type 9 / TASK_TRIGGER_LOGON). The task itself stays `Enabled=true`; `enable`/`disable` only toggle the trigger's `Enabled` flag, so a disabled autostart still allows manual `start`; unelevated calls may complete through a controlled `runas` elevation and report `AUTHORIZATION_CANCELLED` / `INSTALL_USER_MISMATCH` / `ADMIN_ACCOUNT_REQUIRED` / `LAUNCHER_NOT_FOUND` for the respective failures. Linux: `systemctl --user enable|disable e-launcher-host.service` only — the launcher never enables linger and never disables an existing one.
- `pibot-host setup-shower` — Windows only. Explicitly stops the local Host if running, runs `shower-windows.exe shower-setup --state-dir <abs>` (Shower credential onboarding: account-password prompt, verification inside a temporary RDP child session, then save to the current user's Credential Manager), and starts the Host again if it was running, preserving the original error. Budget is 300 s; callers must warn that the local Host is briefly stopped, and an already-occupied session reports busy instead of being taken over.
- `pibot-host pair --center-url <url> [--name <displayName>] [--port <port>] [--data-root <path>] [--center-ca-file <path>] [--force]` — Logs in to Center as owner (password read from `E_LAUNCHER_OWNER_PASSWORD` or first line of stdin), registers this machine's real Host identity via `POST /api/devices` (the center accepts an optional existing `deviceId` to keep the same ID, and an explicit `replaceExisting` rebind rotates the token while keeping the ID and registration record), then persists `config.json` and `secrets.env`. Pair only registers and persists — it does not enable autostart or start the service: CLI users run `pibot-host enable` / `start` next, while the desktop UI performs those steps automatically and keeps a visible retry when one fails. The result keeps `deviceId`/`deviceToken`/`centerUrl`/`displayName`/`controlUrl` and adds `running`/`ready`/`autostart` plus `warnings` describing the post-registration state.
- `pibot-host adopt --center-url <url> --device-id <id> [--name <displayName>] [--port <port>] [--data-root <path>] [--center-ca-file <f>]` — Adopts an existing registered device (token read from `E_LAUNCHER_RELAY_TOKEN` or first line of stdin). A `--device-id` that does not match the device the supplied token belongs to fails `DEVICE_ID_MISMATCH` and never overwrites the existing Host data.
